# Agent capability inventory

## What it is

The resident and employee assistants expose typed Worker tools for the same actions available in the corresponding web workspaces. This inventory maps user-visible actions to those tools and records where the API is still narrower than the requested experience.

## How it works

Each tool in `apps/worker/src/features/agents/tools.ts` builds a fixed `/api/v1` route and calls its existing feature handler. The resident assistant can start as a guest, but profile, saved items, and applications require an applicant token. Employee tools use the organization bound to the employee conversation; a model argument cannot select another organization. Reads run immediately. Writes create a 30-minute proposal and require explicit approval, then the feature handler rechecks current identity, ownership, role, organization, and state. Target edits with a readable `updatedAt` also compare the proposal's record version before execution. The approval supplies a stable idempotency key to handlers that support it.

### Remaining gaps

- Proposals for existing profile, saved-item, external-preparation, feedback, hiring, program, and taxonomy edits now include `changes` with the authorized prior value and exact value sent to the handler. Creation, messages, and some specialized actions still show the submitted fields, while the web review surface renders the available diff. Keep issue #28 open until every mutation and the manual counterpart are complete.
- Duplicate detection compares substantial normalized text and category within a municipality. It does not infer a street address or precise neighborhood, and short generic reports do not generate a match. A resident may explicitly confirm a distinct issue or recurrence before overriding a match.
- The assistant cannot upload binary evidence or résumés by a JSON tool call. `prepare_resume_upload` returns the protected multipart route and file-picker metadata after applicant authorization; the web composer performs the upload. Feedback evidence currently enters as bounded inline data in the manual report form. Full agent evidence parity needs a staged, owner-scoped upload API whose opaque asset ID can be attached to a reviewed feedback proposal; do not put raw bytes into model arguments or D1 proposal rows.
- Browser-only actions such as opening an official site, dragging a file, and downloading a generated document stay in the client. A tool may return a protected download path or official handoff but cannot claim that a browser navigation or external submission occurred.
- No source administration or personal/organization settings API exists yet. The agents can inspect source provenance; language selection and session controls are client preferences rather than Worker data mutations.

## How to change it

When a manual Worker action is added, add a fixed route, validated arguments, method, handler, mode, and access level in `tools.ts`. Add stale-record checks in `recordVersion` in `index.ts` for edits to existing records when a read route exposes a version. Keep binary uploads in a client file control unless a dedicated, bounded upload tool is designed. Update this table and `docs/agents/conversations.md` with each capability.

## Configuration

The assistant uses the same Auth0, D1, R2, Tiger, and source configuration as the manual Worker handlers. `FEEDBACK_ABUSE_HMAC_KEY` signs repeatable guest receipt tokens for approved feedback proposals. The Workers AI model and free-credit cap apply to natural-language turns; direct typed tool calls do not spend model inference.

## Dependencies

`apps/worker/src/features/agents`, the existing feature handlers, the shared permission model, D1 proposal storage, Cloudflare Workers AI for conversational selection, and the web/native clients that render previews and file controls.
