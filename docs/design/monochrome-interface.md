# Envoy web interface

## What it is

The web app uses one light shell for resident discovery, feedback, applications, profile management, agent chat, and staff work. Restrained color and small paint accents distinguish major workspaces; content and status remain readable without color. The desktop rail becomes a drawer on narrow screens. Page names appear in a small breadcrumb; chat starts with a centered prompt and composer.

## How it works

The shell adds a 220 ms opacity and slight lift entrance only when its page key changes. Discovery areas, application views, program views, and staff workspace tabs have distinct keys; selecting a record within a list keeps the same key. The animation is a CSS effect on the newly rendered main area, so the header, rail, outer padding, and borders stay in place. Browser reduced-motion preference removes the entrance.

`apps/web/src/platform/main.ts` owns the rail, breadcrumb, resident and employee chat, feedback receipt, and staff case detail. The rail exposes connected destinations directly with distinct Lucide icons. Resident Explore mounts `apps/web/src/features/discovery/`; Participation mounts its public consultations page; Profile mounts `apps/web/src/features/profile/`. Public applications and programs mount `apps/web/src/features/applications/` and `apps/web/src/features/programs/`; the latter embeds program intake for requests and sponsorship. Official external application preparation mounts `apps/web/src/features/external-preparation/` for a selected discovery record. Staff workspace views mount `apps/web/src/features/staff/`. Staff Inbox loads the real feedback queue and opens a case through the Worker's detail route.

The chat composer sends to the Worker's conversation API. Empty resident and staff chats show three role-specific prompt cards below the composer. A card fills the editable draft and focuses it; it never sends a message. Prompts map to supported discovery, feedback, hiring, theme, and program-intake tools. The plus button anchors a compact area, files, feedback, and available-tools menu to the composer. The tool picker lists tools returned by the conversation, so residents and employees see their own authorized tools. The rail has no Plugins entry because users cannot manage the tool set. Read tools with no arguments run directly; other tools fill an editable request for the assistant. Write actions show a proposal card and require approval. A feedback proposal has an editable report message, a plain destination notice, and an explicit acknowledgement. If the message changes, the button creates a new typed `create_feedback` proposal and rejects the prior version; the changed wording is never approved in the old proposal. For an existing-record write, `preview.changes` shows the authorized current value beside the proposed value in a compact review table. Missing, empty string, empty list, and empty object values have distinct labels; nested values render as text-formatted JSON, so they cannot inject markup. Writes without a diff retain the readable body-field preview. Proposal cards omit request paths, methods, and internal flags. A proposal marked `requiresSandboxAcknowledgment` also requires a checked practice-destination acknowledgement before approval. The sidebar omits the sandbox disclosure because the relevant submission step and record show it. Recent authenticated conversations come from the Worker; guest conversation IDs and bearer tokens remain in tab-scoped storage. The rail search icon opens a conversation search dialog. The area picker currently selects Toronto and includes that context in the sent message.

The plus menu and Files tray use the actual résumé upload endpoint for signed-in applicants. Dropping a PDF or DOCX onto the composer uses the same upload; a saved-file chip links to Profile. The agent's `prepare_resume_upload` read result opens this existing Files tray and focuses its file control. The result carries an upload path and field name, but no file bytes; the browser sends the selected file directly through `api.uploadResume`. The UI checks that this is the known profile upload handoff before suppressing the raw tool JSON. Guests land on a dedicated sign-in page and return to the chat upload menu after authentication, where they choose the file again. File contents are never inserted into a chat message. The sign-in page offers personal and staff Auth0 entry points; its local identity control appears only in development. Guest-only navigation to authenticated pages is visibly disabled. The microphone requests a signed ElevenLabs voice session and inserts finalized user utterances into the editable text field. The browser passes the short-lived session token as the provider user ID and a private dynamic variable. After disconnect it polls `/voice/session/status`; a signed post-call submission with explicit spoken confirmation is shown only after the Worker returns the matching private receipt. Unsubmitted or duplicate outcomes keep the editable draft, and the browser does not submit a second copy. A short standalone confirmation utterance is omitted from the draft. The composer shows a compact Envoy model menu and a three-position thinking preview slider. Both are presentation settings: the Worker still uses its configured `@cf/ibm-granite/granite-4.0-h-micro` model at fixed effort; the menu says replies use one fixed model without exposing the provider name. The private feedback receipt and staff case detail show real activity and properties. Staff routing, request-details, outcome, reply, and remaining status controls call Worker routes. Evidence filenames are displayed as metadata because protected downloads require an authenticated request.

The manual feedback page uses a two-step Write / Review and send layout. The main report field remains prominent; optional improvement text is behind a native disclosure, and the existing voice control remains next to the report field. The private receipt retains its case-detail layout. The styling is scoped to `apps/web/src/features/feedback/feedback.css`, so staff case surfaces are unaffected.

Manual feedback review calls `/feedback/duplicate-check` with the message and selected municipality before enabling submission. A strong match shows only the existing case status. A resident can explicitly mark the report as a different issue or recurrence and submit with `duplicateOverride: true`; ordinary submissions leave that flag false. The create route also checks duplicates to cover a match that appears between review and submit. A chat report proposal shows the same status-only duplicate notice. It requires a separate recurrence checkbox plus the destination acknowledgement before an override approval; a duplicate found during approval updates the pending proposal instead of creating a receipt. Neither surface displays another resident's report text, case ID, or receipt token.

## How to change it

`transitionPageKey()` in `apps/web/src/platform/main.ts` defines which navigation changes animate. Keep record IDs and transient state out of that key. `render()` remains synchronous because focus restoration after menu and dialog actions depends on the new controls existing immediately. If a new top-level route is added, decide whether it deserves its own key; keep same-page data and composer updates animation-free. The timing and motion are in `apps/web/src/platform/styles.css` under `.page-route-enter`.

Update `navigation()` and `mainPage()` together when adding a route, and keep the destination backed by a working API or module. Update both `packages/i18n/src/en.ts` and `fr.ts` for visible text. Prompt cards are defined in `chatPromptCards()` and should use capabilities present in the Worker tool registry; keep them as draft-only actions. New chat tools belong in the Worker tool registry; the UI reads its list at conversation creation. Add a zero-argument read tool to `DIRECT_READ_TOOLS` only if it can be invoked without arguments. Keep the approval preview for writes. To extend an existing-record diff, add a human-readable `field` and JSON-safe `before`/`after` values to the Worker's `preview.changes`; `proposalChanges()` renders those values, while `proposalFields()` remains the fallback for writes without a diff. Case properties come from `FeedbackClientReceipt`; add fields in the Worker and API type before showing them here. The shell CSS is in `apps/web/src/platform/styles.css`; feature modules own scoped CSS.

The selector label and slider options are in the shared locale catalogue; `chatModelMenu()` owns their local presentation state. Do not pass those values to the Worker until the conversation API exposes a corresponding supported model and effort contract. Keyboard users can Tab to the range control, adjust its three positions with arrow keys, and dismiss the menu with Escape. The menu aligns with the composer’s right edge on phones; the chat textarea uses the composer’s rounded focus halo rather than drawing a rectangular focus ring inside it.

Use real Auth0 tokens before the development identity fallback. The fallback selector appears only on the sign-in page in Vite development builds. `SIGNIN_INTENT_KEY` in tab-scoped storage returns a newly authenticated applicant to their intended route; résumé intent returns to the chat upload menu because browser redirects cannot retain the selected file. A guest may use resident chat and submit feedback without signing in; staff pages require an employee token and organization role. Keep the final sandbox acknowledgement when changing submission copy or flow. Keep duplicate preflight fail closed and reset any override when the draft or duplicate status changes.

## Configuration

`VITE_API_BASE_URL` selects the Worker API base URL; local default is `http://localhost:8787/api/v1`. Root `scrollbar-gutter: stable` reserves space so route changes do not move the shell horizontally. The Auth0 SPA client, audience, domain, and staff organization are configured in `apps/web/src/platform/auth0.ts` with `VITE_AUTH0_*` overrides. Locale persists in `localStorage` as `civicresolve.locale`. Private receipts and guest chats use `sessionStorage`. `pnpm-workspace.yaml` enforces a 14-day minimum release age for dependencies. The rail switches to a drawer at 620 px; case properties stack at 760 px.

## Dependencies

The shell uses shared contracts, i18n, design tokens, Lucide static SVGs, and the Worker feedback, application, staff, discovery, profile, agent, voice, and emergency endpoints. Auth0 SPA handles sign-in. ElevenLabs browser code loads only after the microphone is chosen. The emergency action asks the Worker for `emergency: true` guidance and does not create a report.

## Focused checks

On 2026-09-26, local browser checks at 1280, 390, and 320 pixels confirmed a 220 ms entrance on Assistant → Jobs, Jobs → Assistant, Assistant → Nearby, and Nearby → Feedback. The header height and each route’s outer padding were not animated, and no horizontal overflow or runtime errors appeared. Same-page locale rerenders, discovery result selection, and the chat plus menu produced no running route animation. Emulated reduced motion removed the animation name.

On 2026-09-26, the model popover was inspected at 1280, 390, and 320 pixels in English and at 320 pixels in French. It stayed within the viewport without horizontal overflow or runtime errors. A keyboard ArrowRight moved the native range from Standard to Deep and updated `aria-valuetext`; Escape closed the menu and returned focus to the model button. The textarea drew no inner outline while the rounded composer showed the focus halo.
