# Discovery and applicant profile on the web

## What it is

The resident web workspace has a source-backed discovery view for jobs, support, funding, nearby services, and participation, plus a private applicant profile and résumé workspace. Public discovery shows reviewed records only. Local developers can opt into practice records with `?practice=1` on the Vite development origin; production discovery has no practice toggle.

## How it works

`createDiscoveryPage({ area, locale, token })` renders an independently managed view. Areas are `all`, `jobs`, `support`, `funding`, `nearby`, `participation`, and `saved`. A keyword and city/location search calls `/api/v1/discovery` with `q`, `location`, freshness, and pagination filters. On wide screens, results and the selected record sit side by side; on a phone, choosing a result opens its detail with a return control. Result labels distinguish an individual official posting from a finder, a verified participating listing, or a physical service location. A detail view shows publisher, freshness, review date, language, and terms links. The official action calls the handoff endpoint and opens the returned HTTPS publisher URL. Visitors finish any application or consultation on the publisher’s site; Envoy does not record that submission.

The Nearby area calls the public `/api/v1/nearby` route, which returns reviewed public services with categories (`government`, `library`, `community`, `transit`, `other`). Category chips filter on the server. A tiled MapLibre map is the default canvas, with city search and filters alongside it on desktop and stacked above it on phones. Nearby loads up to 100 records per page so the current source directory can be shown on one map. Only records with source-backed coordinates and `service.pinEligible` become markers; a marker selects the same source detail as the list. The List switch preserves every matching service, including records without a map pin. If tiles, WebGL, or coordinates are unavailable, the map switches to the list. A station-level coordinate is labeled approximate in detail. Service detail displays sourced public access, services, hours, and accessibility facts with each fact's verification state, date, and source link. It never claims a place is open now. When no location is entered, results are sorted by jurisdiction and name, not distance.

Jobs, Support, and Funding share the search form and results API but use distinct introductory structures inside one search surface. Jobs now defaults to individual source-backed postings (`type=job_posting`) with the employer, location, closing date when known, effective application status, and direct official posting handoff. Date-only closing values are displayed without inventing a cutoff time. A separate `type=jobs_finder&includeFinders=true` request supplies a quiet Official job boards section when at most three individual postings match; those directory links are never presented as vacancies. If the directory request fails, the section links directly to the Government of Canada’s Job Bank. The introduction contains only real source-browsing actions and jurisdiction shortcuts; no individual opening or eligibility is implied by those shortcuts. The dedicated Participation page calls `/api/v1/consultations` for its own sourced opportunities and official handoffs.

When a search has no reviewed records, the view shows a compact empty state and offers to clear active filters. The Jobs fallback links to the Government of Canada’s [Job Bank search](https://www.jobbank.gc.ca/jobsearch/jobsearch) when no reviewed directory link is available. This link is an external search handoff, not an imported posting or a submission recorded by Envoy.

Signed-in applicants can save a record and maintain up to 12 personal checklist steps. The view calls `/api/v1/discovery/saved` and passes `includeSamples=true` only for the local development `?practice=1` fixture mode. Guest search works without a token; saving requires an applicant token.

The shell can pass `onPrepare(recordId)` to route a permitted `official_external` record to Envoy’s external preparation page. Jobs, support, and funding use a “Prepare application” action; service locations and consultations use visit/participation wording. The publisher handoff remains a separate action. Practice records and records without a permitted official handoff do not show this preparation action.

`createProfilePage({ locale, token })` loads the owner’s `/api/v1/profile`, résumé list, and applications. The form and document workspace appear in separate outlined sections on wide screens and stack on phones. Applicants can edit contact details, skills, education, and experience manually. The document area accepts a selected or dropped PDF/DOCX file; extraction shows literal suggestions alongside their source snippets. Choosing a suggestion changes the draft only. The applicant must save the profile. A separate action shares a selected résumé with a selected existing application through `PUT /api/v1/applications/{id}/resume`. Deleting a résumé also revokes its application links on the Worker.

## How to change it

The view factories and local state live in `apps/web/src/features/discovery/index.ts` and `apps/web/src/features/profile/index.ts`. Jobs, Support, and Funding structures live in `area-structures.ts`; the root shell mounts the separate Participation module. The Nearby tiled map lives in `nearby-map.ts` with its own CSS; the discovery view owns its search/sidebar layout and map/list selection. Their CSS is scoped under `.discovery-*` and `.profile-*`; avoid adding a global card accent or oversized heading. The root shell imports the factories and chooses an area based on navigation. User-facing English and French strings are colocated in the modules. If the Worker response shape changes, update the local view types and the shared contract; if profile fields change, update `packages/domain/src/profile/index.ts` too. Keep Jobs `listing.applicationStatus` tied to Worker status logic and use `sourceUrl` only for official board links. Keep Nearby category filters and map pin eligibility tied to the Worker's sourced metadata; do not infer them from titles or coordinates alone.

The Worker owns permission and source trust checks. The client must keep sample records opt-in, must not fabricate live openings or deadlines, and must not treat an external handoff as a completed submission. Résumé extraction should continue to require a separate choice before updating the draft, and sharing should remain a separate explicit action.

## Configuration

`VITE_API_BASE_URL` selects the Worker API base URL and defaults to `http://localhost:8787/api/v1`. `VITE_MAP_STYLE_URL` may point to an HTTPS MapLibre style; the default OpenFreeMap Liberty style needs no key. The factories receive the current `en` or `fr` locale and an applicant access token, or `null` for a guest. The Worker requires D1 discovery migration `0013_discovery.sql`, the profile migration `0004_profile.sql`, private `PRIVATE_ASSETS` R2, and Applicant role permissions. Upload size and storage limits are enforced by the Worker, with a 5 MB UI hint.

## Dependencies

The web views use browser `fetch`, `FormData`, and DOM APIs, MapLibre GL JS with OpenFreeMap tiles, Lucide static icons, the shared profile and locale contracts, the Worker discovery/nearby/consultations/profile/application routes, D1 source records, and private R2 résumé storage. No map token or paid client service is needed to use these pages.
