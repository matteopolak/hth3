# Resident and employee conversations

## What it is

The Worker hosts persistent English and French Envoy resident and employee conversations. Residents can start as guests; employees need a current Auth0 organization role. Both call typed tools backed by the corresponding manual API operations. Writes become reviewable proposals and run only after an explicit approval request. The [capability inventory](capability-inventory.md) lists the tools by workspace action and names the remaining gaps.

## How it works

`POST /api/v1/agent/conversations` with `{ "mode": "resident", "locale": "en" }` creates a conversation. A guest receives a 64-character `conversationToken` and must send it as `X-Conversation-Token` on subsequent requests. Signed-in conversations bind to the current Auth0 subject; employee conversations also bind to the organization. A platform curator with a global taxonomy permission supplies `organizationId` when creating an employee conversation for a selected organization. `GET /api/v1/agent/conversations` lists signed-in threads. `GET /api/v1/agent/conversations/{id}` returns history, pending proposals, and the mode's available tools.

`POST /api/v1/agent/conversations/{id}/messages` accepts `{ "message": "..." }`. The Worker sends bounded recent history and a role-specific tool catalog to the `@cf/ibm-granite/granite-4.0-h-micro` Workers AI model. Workers AI currently returns an OpenAI Chat Completions envelope, so the Worker reads `choices[0].message.content` as well as its older top-level `response` shape. A model-selected read tool runs through the existing Worker feature handler. A model-selected write tool creates a proposal. For a non-emergency service problem explicitly placed in Toronto, the Worker checks for a strong recent match before preparing feedback from the resident's original words. A match returns only the existing case's current status; the assistant asks whether this is a separate issue or recurrence and creates no proposal until the resident confirms, including a short “yes” in direct reply. It then uses the earlier issue description, so a short follow-up does not replace the original report text. The match check runs again on approval. If the municipality is unclear, the assistant asks before choosing a destination and can continue when the resident replies “Toronto.” The private queue destination is disclosed on the action preview and must be acknowledged on approval. The client may also invoke any exposed tool directly with `POST /api/v1/agent/conversations/{id}/tools` and `{ "tool": "list_postings", "args": {} }`; this keeps manual agent controls usable when tool selection is imperfect.

The Worker recognizes direct requests to prepare feedback and common service issue descriptions, including damaged public fixtures, before relying on model tool selection. A model sentence is not evidence that a tool ran: the Worker replaces preview or completed-action claims unless a proposal was actually stored, and uses a fixed preview-ready reply after a successful write proposal. The message response includes the proposal object that the client renders as a card. A request to prepare a preview never submits feedback; submission stays behind the separate approval endpoint.

Employee workspace tools use the existing protected `/staff/organizations/:orgId/workspace` routes. Saved views and reports can be listed, opened, run, created, edited, and deleted; settings expose a personal default tab and an organization reporting window as separate writes. The proposal body carries each item's `expectedVersion`, and the agent also captures the protected current version when making the preview. The underlying handler checks employee ownership, organization membership, feedback permission, administrator role for the organization setting, and idempotency again on approval. A report result contains exact counts and recent source IDs, not private case text.

The `tools` response lists exact names and access levels. Resident tools cover sourced discovery and official handoffs, saved items and checklists, public postings and participating programs, private profile and résumé actions, external application preparation, first-party job and program applications, feedback receipts and follow-up, and emergency guidance. Employee tools cover organization feedback, assignment and outcomes, applications and messages, analytics, theme review, organization posting and program lifecycles, taxonomy versions and publication, and classification correction. Protected evidence and résumé downloads return authorized paths rather than feeding raw files to the model. `prepare_resume_upload` first checks access using the résumé list route, then returns `{upload:{path:"/api/v1/profile/resumes",method:"POST",contentType:"multipart/form-data",field:"file",requiresFileChooser:true,submitted:false}}` so the client can offer its existing file picker. `prepare_feedback_evidence_upload` requires a pending resident feedback proposal and returns the conversation-scoped multipart path. The client lets the resident choose or drop a PDF, PNG, or JPEG, uploads it outside model arguments, then attaches its opaque asset ID to that proposal. The feedback card displays the attached filenames before approval. Binary upload remains a client action; the agent can use already uploaded assets. New manual API actions should be added to `apps/worker/src/features/agents/tools.ts` when introduced.

Resident feedback evidence is staged outside model calls. Upload a selected file to `POST /api/v1/agent/conversations/{id}/feedback-evidence` as multipart field `file`; the current conversation credential scopes the private R2 object and D1 row. The response returns an opaque asset ID and file metadata. Attach that ID to a pending `create_feedback` proposal with `POST /api/v1/agent/conversations/{id}/proposals/{proposalId}/feedback-evidence` and `{ "assetId": "asset_..." }`. This route adds the ID to server-owned proposal arguments and safe metadata to the preview; model-supplied evidence IDs are stripped. On explicit approval, `create_feedback` verifies the conversation owner or guest token, re-scopes the staged object to the new submission, and returns it through the ordinary receipt attachment list. Uploads accept one PDF, PNG, or JPEG up to 5 MiB; each conversation can stage at most three files and 10 MiB total. Staged evidence cannot be attached or submitted after 24 hours. Rejected or expired proposals do not publish file links.

Writes are stored in D1 with a path, method, body, destination, and expiry in a preview card. New feedback, applications, postings, and programs show their submitted content fields as `changes:[{field,before:null,after}]`. Existing-record edits compare an authorized read with only the fields the typed write sends; unchanged and omitted fields are excluded. Messages appear as a new row, alongside status changes where the same action makes one. Reusable answers and résumé deletion use private owner reads; theme membership uses the authorized source list. The preview does not treat a separate sandbox or duplicate acknowledgment as a saved record field. `POST /api/v1/agent/conversations/{id}/proposals/{proposalId}/approve` with `{ "approved": true }` executes one proposal; `.../reject` discards it. New feedback and applications to a practice program require the separate `{ "sandboxAcknowledged": true }` approval field. A matching feedback report leaves the proposal pending with `requiresDuplicateOverride`; a separate, explicit `{ "duplicateOverride": true }` approval is required if the resident confirms this is a different issue or recurrence. An initial approval cannot bypass a match discovered during approval. An approval expires after 30 minutes. The Worker derives a stable idempotency key and reruns the underlying API handler with the caller's **current** Authorization and receipt token headers, so role, ownership, organization, status transition, and target checks happen again. For edits to an existing record with a readable version, the preview captures `updatedAt` or a bounded theme snapshot and rejects a stale approval. Resident feedback receipt tokens are HMAC-derived from the proposal and returned only to the client, never saved in conversation history or proposal results.

Each tool links to the same `/api/v1` resource as its manual counterpart. A guest reading or replying to feedback must pass `X-Receipt-Token`; the model never receives the token. A signed-in applicant action requires the same Auth0 permission as the manual API. A staff action is restricted to the actor's organization and role. No model output can directly execute a write.

## How to change it

Add a new typed entry in `apps/worker/src/features/agents/tools.ts`, with a fixed route builder, parameter validation, method, target feature handler, and `read` or `write` access. Add the matching field selection in `proposal-changes.ts`; new records can use a null prior value, while existing records require a protected read and a `VERSION_READ_TOOL` entry in `index.ts`. Compare only the typed write body and return no guessed prior values. Avoid accepting arbitrary URLs or an organization ID from model arguments. Update `systemPrompt`, `requestsFeedbackPreparation`, and the action-claim gate in `apps/worker/src/features/agents/index.ts` when the assistant's behavior changes, and add the corresponding UI preview/rendering. The table migration is `packages/db/migrations/0007_agent_conversations.sql`. Keep tool payloads small and exclude access tokens, private receipt tokens, and raw uploaded files from stored arguments or model messages.

## Configuration

`[ai] binding = "AI"` in `apps/worker/wrangler.toml` provides Workers AI. The model and 200-inference-per-UTC-day application cap are in `apps/worker/src/features/agents/index.ts`; the cap is persisted in D1 to limit free-credit use. `FEEDBACK_ABUSE_HMAC_KEY` must have at least 32 characters for feedback approval. Auth0 variables and D1/R2 bindings are shared with the existing Worker. The Worker must allow the `X-Conversation-Token` CORS header. There is no paid AI fallback: if the binding or free quota is unavailable, message generation returns `AI_UNAVAILABLE`, while direct read tools and proposal approvals still use the Worker API.

## Dependencies

Cloudflare Workers AI, D1, existing Auth0 identity mapping, application, profile, source, and feedback feature handlers. The browser and SwiftUI clients keep the guest conversation token securely and render proposal cards with a clear approve/reject choice.
